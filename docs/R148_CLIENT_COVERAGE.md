# R148 client proposal acceptance matrix

## Basis and assessment

This matrix follows the four phases in the client's numbered Persian proposal (`client-proposal-extracted.txt`, paragraphs P0001 onward) and preserves the boundaries recorded in `docs/R147_CLIENT_COVERAGE.md`. References such as P0201 identify the client's own acceptance requirements. Code paths are relative to the repository root and identify starting points for the next implementer.

**The repository contains a substantial implemented registry and bounded professional workflows. Acceptance of the complete national platform remains outstanding.** R148 strengthens policy consistency, account security, genetic authority and private evidence handling; it preserves the existing registry, pedigree, import, marketplace, directories, workspaces and alternative interfaces. These changes do not establish institutional authority, representative national data coverage or acceptance on the hosted production system.

“Implemented” below describes a bounded software capability. “Partial” identifies a specific missing part of the proposal. “External acceptance” requires actual data, an authorized institution, a domain specialist or a deployment operator. These conditions can coexist. Final execution results belong in the R148 validation record; this document does not substitute feature counts or a completion percentage for acceptance.

## Gates applying to every phase

1. **Institutional acceptance — P0011, P0190–P0191.** Obtain named data-controller, registration, passport, pedigree, laboratory and event authorities; approved delegation, consent, retention, publication and dispute processes. A configuration value or grant record cannot supply these agreements.
2. **Hosted security and operations — P0183–P0188.** R148 implements TOTP enrollment/step-up, recovery, current-session checks and private evidence protections. Complete actual operator enrollment, key custody/rotation, chosen-provider acceptance, restore/rollback drills, monitoring, incident ownership and agreed recovery objectives. Local SQLite/PostgreSQL tests are evidence of software behavior, not a completed production security assessment. Start at `src/auth/mfa.ts`, `src/auth/mfaGuard.ts`, `src/auth/mfaCrypto.ts` and deployment runbooks.
3. **Data and pilot acceptance — P0196–P0212, P0224–P0232.** Approve the data dictionary and permitted acquisition/redistribution for each source; execute reviewed import samples; publish reproducible coverage and error reports; run the proposal's phase-specific user scenarios. Prefer authorized exports/APIs before commissioning additional crawlers. Set delivery dates and budgets from these measured dependencies, and retain the existing accepted features throughout.

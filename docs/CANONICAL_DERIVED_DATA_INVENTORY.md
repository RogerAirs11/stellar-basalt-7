# Canonical vs Derived Data Inventory

Authoritative classification of every migrated table and virtual table (post-package delta D05).
This document is machine-checked by `tools/validate-operational-inventories.mjs` (wired into
`npm run check`), which derives the migrated structures from all applied migrations and fails if any
ordinary/virtual table is missing here or a documented structure no longer exists in migrations.

Classification vocabulary:

- **canonical / authoritative** — source of truth for registry facts; must never be discarded as rebuildable.
- **operational / durable workflow state** — must survive recovery; records intent, workflow or access state.
- **derived / rebuildable** — may be reconstructed from canonical state by a documented rebuild mechanism.
- **ephemeral / maintenance** — safe to recreate/clear only under the documented conditions.

## Key recovery semantics (must be preserved by any restore/rebuild procedure)

1. **Canonical first.** `horses`, `people`, `horse_people`, `horse_aliases`, `data_quality_issues`,
   `source_imports` and `users` are authoritative. Derived search/analytics/read-model structures are rebuilt from them.
2. **The journal is the recovery authority for workflow mutations.** A `canonical_mutation_log` row with
   `status='committed'` and `audit_status='pending'` means the canonical/workflow mutation committed durably
   and the audit row may still be reconciled after a failure — final audit/search settlement may be pending
   and is reconciled by `POST /api/admin/maintenance/reconcile-mutations`. "Every write has an audit event"
   is therefore *durable intent + reconcilable settlement*, not a synchronous guarantee.
3. **Search is derived.** `horse_search_source`, `horse_search_fts` and `horse_search_trigram` may be fully
   rebuilt by enqueueing every canonical horse onto `horse_search_reindex_queue` and draining it in 3-job batches.
4. **Analytics is gated, not assumed current.** `registry_state.analytics_stale` and source revision must be honored by every
   consumer. Heavy `/api/analytics/registry` refuses stale analytics; hot operational endpoints use snapshot data only when fresh and otherwise run their exact live fallback.
5. **Hot read models are derived.** `registry_runtime_counters`, `person_registry_stats`, `horse_registry_people_summary`, `registry_filter_counts` and `horse_role_search_trigram` move repeated request-time work into deployment/mutation-time maintenance. `registry_runtime_counters` is transactionally maintained on supported horse create/archive writes; the other candidate read models are admitted only while revision-fresh. Stale People/profile/display-name paths fall back to exact canonical SQL, and the role trigram is bypassed. They never replace canonical facts and may be rebuilt after restore.
6. **Portable backup set.** Canonical + operational tables (including `canonical_mutation_log`,
   `registry_state`, `audit_events`, workflow tables, `content_posts`, AI conversation/accounting tables, `sessions`) belong in a portable backup. Derived and
   ephemeral structures may be omitted and regenerated after restore.

# Independent client coverage review — current R147 implementation

Reviewed the original client request in `review-r147/input/original-request.md`, the numbered Persian proposal in `review-r147/input/client-proposal-paragraphs.txt`, current implementation source, route tests and available local evidence. Proposal references below use its `P####` paragraph identifiers. Paths beginning `src/`, `tests/`, `tools/` or `docs/` are relative to the repository root.

**Assessment:** the application now has a substantial, tested local registry core and coherent private care/laboratory capabilities. It does not yet demonstrate delivery of the entire four-phase national platform with qualified operational data, institutional authority and production acceptance. A source completion percentage would obscure these separate conditions.

**Status meanings:** **Implemented locally** means the stated bounded behavior is supported by inspected code and execution evidence, not institutional or production acceptance. **Partial** identifies a real implementation plus a specific unmet portion of the client's wording. **External decision/data** cannot be established by writing code or selecting an environment flag. These statuses can coexist.

## Remaining P0 gates before a real sensitive-data or “official national” release

These are release acceptance gates, not claims that every item is an exploitable source defect.

1. **Authority, access and publication decisions.** Obtain a signed scope matrix naming the data controller, passport/pedigree/result confirming authority, practitioner/lab onboarding process, ownership/agent delegation, consent basis and retention/publication rules. Acceptance: each live privileged grant and each official/public assertion resolves to an authorized institution, current assignment and documented basis; revocation/export/withdrawal scenarios pass. A configured agreement string is not sufficient evidence. Relevant: P0011, P0030–P0056, P0190–P0191; professional grants, publication and care activation code.
2. **Acquisition versus redistribution permission.** For each intended source, establish permitted acquisition method (API/export/manual entry/authorized crawl), fields, purposes, retention, redistribution, cadence and revocation handling before ingesting actual protected material. Acceptance: source registry and raw import manifest reference the actual authorization; restricted data stays private through create, update, claims, search, derived results and exports; source withdrawal is rehearsed. Public web availability is not itself a recorded permission. Relevant: `imports.ts`, `fieldClaims.ts`, source agreements and publication tests.
3. **Privileged access and deployment operations.** Complete MFA enrollment/recovery/step-up policy for sensitive roles; separate the preserved legacy genetics `horse.edit` allowance into approved scoped result/evidence/review/publication permissions (see P0-05 in the main handoff); rehearse migrations, restore and rollback on the chosen hosted stack; verify access/configuration, logs, rate limiting and incident ownership. Acceptance: role alone cannot acquire private genetic evidence, scoped reviewer workflows remain usable, recorded restore result meets agreed RPO/RTO, hosted concurrency/security acceptance exists, and named owners sign the pilot launch checklist. Local PostgreSQL success is useful evidence but does not supply these operational decisions.
4. **Operational-data qualification.** Obtain the actual intended registry/competition/lab exports and an authorized data dictionary. Acceptance: a reproducible manifest reports real, synthetic, restricted and publishable cohorts separately; identifier namespaces, duplicates, missingness, seven-generation coverage and racing crosswalk quality have reviewed samples and documented unresolved conflicts. New implementation tests used fictional records. Historical database counts do not establish the current dataset or permission status.
